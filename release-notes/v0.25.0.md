# I'm sorry, Dave. I'm afraid I can't do that.

Some knowledge should stay as it is: a domain can now be locked, an agent account can write in one place and read everywhere else, and a full reindex of a large domain takes seconds instead of minutes.

## New & Noteworthy

**Read-only domains.** A curated handbook, a frozen archive, a team domain you only follow: until now any agent could still write into it. Set `read_only: on` in the domain policies and every write through Crystalline is refused. That holds for agents over MCP, people in Fluid, the CLI and the REST API. The answer is always the same sentence: "'archive' is read-only; its owner switches read_only off in the domain policies". So an agent knows at once what happened and does not try three other ways.

- Only the domain's owner or an instance admin switches the flag.
- An agent can lock a domain when you ask it to. It cannot unlock it. Over MCP every way to switch it off is refused, for every caller, and the agent is told to ask the owner. A person switches it off in the domain policies in Fluid (or with `PATCH /domains/{domain}/manifest`).
- Team pulls still apply. `update_domain` keeps a read-only copy current. Sharing is refused, since nothing local can change.
- Evolve and the write nudges leave a locked domain alone. Nobody could act on its findings. They come back when you unlock it.
- The flag guards what goes through Crystalline. An agent with a shell can still edit `MANIFEST.md` on disk. It is not a sandbox.

**You see where you can write.** `list_domains`, `browse_domain` and `read_engram` say `read_only: true` for a domain you cannot write: it is locked, your role is viewer, or it is not on your write list. The routing block marks it "(read-only)", so an agent does not plan a write there in the first place. Fluid shows a lock on a locked domain and does not offer edit, new, move or delete where you cannot write. A domain from a connected server shows its server's mark.

**Agents that read everything and write in one place.** One shared server, many agents. Each agent gets its own account and token, reads every company domain and writes only to its own. Give the account a write list:

```bash
crystalline users add bot --mcp-token bot --role editor --writes agents-bot
crystalline users writes bot agents-bot,shared-agents
crystalline users writes bot --clear
```

An entry is a domain name or a prefix with `*` (`agents-*`). A domain that is not on the list is read-only for that account, on every surface. The refusal says why: "'handbook' is not on the write list of 'bot'; an instance admin changes it with crystalline users writes". `crystalline users list` shows the lists. A list only takes rights away: a viewer with a list still writes nothing.

**A full reindex is fast again.** A full reindex of a large domain took 10 minutes and more, the first index about 4. The cause was a lookup that read the whole domain for every engram. At 50,000 engrams:

- Embedded database: first index 202 s to 7.5 s, full reindex 430 s to 12 s.
- Postgres: first index 290 s to 85 s, full reindex up to 173 s to 99 s.

## Fixes

- A share into another person's open proposal told you to "merge or withdraw first". You cannot withdraw someone else's proposal. It now says to share again once that proposal is merged or closed.
- When a direct share was refused and Crystalline could not save that refusal, the share failed with an error and the offer of a proposal was lost. The refusal now comes through.
- The share preview and the share itself could give different reasons for the same refusal. They now check in the same order.
- After you discarded a draft, links to it from other people's drafts still showed as resolved until the next sync.
- `configure` with a domain showed the folder's policies to someone whose draft had deleted the MANIFEST. It now shows the MANIFEST as missing for that person.
- A failed `.crystalline.yaml` write in `configure` came back as an internal error. It now says what went wrong.
- On Windows, a config path that differed only in the case of a letter like Ü gave a false "daemon serves X, not Y" line.
- On Windows, `doctor --fix` needed the MSI to clean up an old daemon task, where removing the old task was enough.
- On Windows, the cleanup of an old daemon task read your account from `USERDOMAIN` and `USERNAME`. It now reads it from the running process.

## Breaking changes

None. Three changes you may notice:

- Over MCP, `share_changes`, `resolve_conflict`, `withdraw_proposal` and `discard_changes` now refuse an instance viewer, as the REST API always did.
- `crystalline status --json` leaves out `config_mismatch` when nothing differs, as `doctor --json` does.
- The domain policies have a fourth row, `read_only`, and `configure` shows it.
